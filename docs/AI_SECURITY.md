# Management Projet assistant security

Identity comes from existing dj-rest-auth JWT authentication. Active-user status and native `can_view`, `can_print`, `can_create`, `can_edit`, `can_delete`/staff behavior are rechecked in trusted backend code. The model cannot grant roles or choose another application/company. Financial reads follow native read access; there is no invented administrator-only financial role.

Schemas reject unknown tools, identity/role arguments, arbitrary filters, invalid dates, oversized searches and unsafe paths. Results contain bounded visible business fields. Object existence and access are checked before reads, navigation, PDF offers, follow-up references and replay. There is no generic SQL, shell, Python, account-management, upload or cross-application tool.

Owned conversations carry a hash of effective native capabilities. Revocation invalidates access before tools, streamed delivery and history replay. History stores revalidated action descriptors; sensitive financial result snapshots do not become an authorization source. Knowledge titles/content are filtered by application, workspace and capability before ranking.

Supported edits/deletes require an owned, five-minute, single-use proposal and a separate confirmation request. The native serializer validates permitted changes. A fingerprint covers the record and project deletion's related records/attachments. Confirmation locks the target and cascade records, then locks/reloads the native user and rechecks expiry/permissions immediately before calling the original native PUT/DELETE view. Native protections, notifications and django-simple-history remain authoritative. Confirmation uses bounded SQL/lock waits. Only field names and target/actor metadata enter the audit, not full financial payloads.

Audit metadata includes actor, application, instruction/request correlation, operation, model release, authorization outcome and timing. Confirmed-write audits survive conversation removal and user deletion; native history records the acting user. Audit administration is read-only and restricted by Django admin permissions. Expired ordinary conversations and read audits can be purged; confirmed write audits are retained.

User/database/document text is untrusted data. Backend checks protect against model prompt injection independently of model refusals. React renders plain text rather than arbitrary HTML. Routes and PDF endpoints are backend-approved. The private provider rejects public/link-local destinations and redirects; its endpoint/key are operator configuration only. Credentials and production data are excluded from source, datasets and browser artifacts.

Verified tests include anonymous access, role impersonation, workspace substitution, indirect unauthorized reads, guessed/missing records, other-user history, revocation, stale/expired/replayed proposals, protected quote deletion, native history attribution, malicious record text, restricted knowledge and unsafe navigation. Real PostgreSQL lock-race tests cover revocation, expiry and changed project children. ASGI/JWT tests cover expiry, revocation and disconnect cancellation. See AI_TESTING.md for current counts and limits.
